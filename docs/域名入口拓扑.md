# 域名入口拓扑

> 为什么会有好几个域名指向同一个站、各自负责什么、以及「换域名时最容易漏掉的那一步」。

## 起因：一次静默的失败

2026-09-23 站点因 Vercel 额度打穿（整站 402 `DEPLOYMENT_DISABLED`）搬到腾讯云首尔自托管。
搬的时候**只改了 DNS，没有把域名从暂停的 Vercel 项目里摘掉**。

后果在一天后浮现：**一部分用户打开网站还是看到「网站已经暂停部署」**。

排查结论（2026-09-24 实测）：

- **DNS 是干净的。** `wave-mod.top` / `www.wave-mod.top` 在阿里、DNSPod、百度、114、
  Google、Cloudflare 以及 CF 权威 NS 直查，全部返回首尔 `43.133.78.46`，TTL 300，
  没有 AAAA、没有残留 `_vercel` TXT。
- **但旧端点还活着。** 带 `Host: www.wave-mod.top` 直打 Vercel 的 anycast IP
  （`76.76.21.x` / `66.33.60.x` / `216.198.79.x`），**六个全部返回 402
  `X-Vercel-Error: DEPLOYMENT_DISABLED`** —— 就是那张暂停页。
  `DEPLOYMENT_DISABLED` 只对**仍绑在项目上的域名**返回（未绑的域名回 404），
  所以这证明 Vercel 那边的域名绑定一直没摘。
- 那个 402 的 `Cache-Control: public, max-age=0, must-revalidate`，
  **浏览器不缓存它** —— 所以残留用户看到它不是页面缓存，而是**DNS 解析到了旧 Vercel IP**。
- 残留来自解析链路上任意一环的陈旧缓存：运营商 DNS 超额缓存、路由器、浏览器/微信
  内置解析器，以及在不同网络（家宽 / 流量 / 公司）之间切换。所以是「有些人、有时候」。

**教训：迁移域名时，改 DNS 只完成了一半 —— 必须把域名从旧平台摘掉。
否则旧平台会继续替这个域名应答，把「DNS 缓存还没过期」变成一张看起来很正式的故障页。**
（这一点已由 `scripts/endpoint-patrol.mjs` 每天自动检查。）

## 三个入口，各管一件事

| 入口 | 地址 | 角色 | DNS 缓存包袱 |
|---|---|---|---|
| 主站 | `https://www.wave-mod.top` | 规范地址。`NEXT_PUBLIC_SITE_URL` 的值，登录/canonical 都以它为准 | 有（本次事故就是它） |
| **抗缓存入口** | `https://go.sunnyrose.xyz` | **全新主机名**，没有任何人解析过 ⇒ 任何解析器第一次查就是对的。给「缓存还没过期」的用户兜底 | **无** |
| 永久发布页 | `https://sunnyrose.xyz` | 独立域名的静态页（CF Pages），主站域名被封时用户从这里找可用地址 | 无（从未指向 Vercel） |
| 旧链接兜底 | `www.wave-mod.top` → 307 → `go.sunnyrose.xyz` | Vercel 上的一个纯重定向项目，接住群里的**历史链接** | 见下 |

### 抗缓存入口为什么有效

`go.sunnyrose.xyz` 是**本次事故前从未存在过的主机名**。没有任何解析器、路由器、
浏览器缓存过它的解析结果，所以第一次查询必然拿到正确的 `43.133.78.46`。
这比「教用户清 DNS」现实得多 —— 用户都是电脑小白，清缓存这种话说不出口也做不到。

服务器侧配置在**独立的 nginx 文件** `/etc/nginx/sites-available/wavemod-alt`
（由 `scripts/setup-alt-entry.sh` 生成，配独立 Let's Encrypt 证书）。
**刻意不并进 `sites-available/wavemod`**：`scripts/deploy-hk.sh` 用 `cat >` 整体覆盖主 vhost，
并进去的话将来任何一次重跑部署脚本都会静默把新入口抹掉。

⚠️ **顺序要求**：本机 nginx 没有 `default_server`，对**未知 Host** 会回落到该端口的
第一个 server block（apex 的 301 块）直接跳到 `https://www.wave-mod.top/`。
所以必须**先加 server_name、再让 DNS 生效、最后签证书** —— 顺序反了，
HTTP-01 验证会因为那个 301 而失败，用户也会被弹回那个有缓存包袱的域名。

### 抗缓存入口上不能登录（设计如此）

`go.sunnyrose.xyz` 定位为**免登录的浏览 + 下载入口**。登录态跨不过去，原因是浏览器安全模型：

- cookie 没有设 `Domain`，是 host-only 的 —— 而 `sunnyrose.xyz` 和 `wave-mod.top`
  是两个**不同的注册域**，没有任何 `Domain` 取值能让 cookie 跨过去。
- 魔术链接 / 微信登录的回调地址来自编译期的 `NEXT_PUBLIC_SITE_URL`
  （`src/actions/auth/auth-actions.ts`），永远指向 `www.wave-mod.top`。

需要登录时走主站。图片不受影响：COS 侧靠 `referrerPolicy=no-referrer`，跨 host 照常显示。

## 旧链接兜底（Vercel 上的 307，2026-09-24 已上线）

小白不会记地址，**他们点的是群里的历史链接** —— 抗缓存入口救不了这些。
所以另有一个只做重定向的 Vercel 项目，见 `infra/vercel-redirect/`
（部署步骤、为什么是 307 而不是 301、什么时候拆掉，那份 README 里写了）。

实测确认的机制 —— **Vercel 边缘按「域名归哪个账号」路由，跟 DNS 指向哪无关**：

| 域名处于什么状态 | 带 `Host` 头直打 Vercel IP 的结果 |
|---|---|
| 绑在**旧账号**那个（暂停的）项目上 | 402 暂停页 —— **尽管 A 记录早已指向首尔** |
| 项目删掉、域名谁都没绑 | 404 `DEPLOYMENT_NOT_FOUND`（残留用户不再看到吓人页） |
| 被**新账号认领**（TXT `_vercel`）之后 | **307 → `https://go.sunnyrose.xyz`** |

所以救这批用户的开关是**认领域名**，不是改 DNS。`wave-mod.top` 本来就挂在旧账号名下
（当年跑在 Vercel 上时认领的，**删项目不会解除账号级的域名归属**），
给新账号加一条 `_vercel` TXT 即可。
⚠️ Vercel 同时会列出 **CNAME `www` → `...vercel-dns-017.com`，那条绝对不能加** ——
那等于把 `www` 整个交给 Vercel，连 DNS 正常的用户也会被甩过去。

最终两类用户都通，且 **A 记录全程一个字没动**：

- DNS 正常的绝大多数 → 直连首尔 `43.133.78.46`，正常进站
- DNS 残留旧 Vercel IP 的 → Vercel `307` → `go.sunnyrose.xyz` → 进站

另一个踩到的坑：`vercel.json` 的 **`/:path*` 不匹配裸根路径**，裸域名
`https://www.wave-mod.top/` 会掉进静态 `index.html` 返回 200（靠页面里的
meta-refresh 也能跳走，但白多一跳），必须额外写一条 `"source": "/"`。

## 巡检

`scripts/endpoint-patrol.mjs` + `.github/workflows/endpoint-patrol.yml`，每天
UTC 02:17（北京 10:17）跑一次，三项检查：

1. 带 `Host` 头直打 Vercel anycast IP —— 还回 `DEPLOYMENT_DISABLED` 就报红
2. `www.wave-mod.top` 从国内/国外公共 DNS 解析 —— 必须仍是 `43.133.78.46`
3. 两个入口自身是否 200（顺带校验证书）

只有 **critical** 让 job 报红（→ 邮件告警）；**warn** 只记录，因为它是可接受的退化
（例如兜底项目拆掉后 Vercel 回普通 404 而不是暂停页）。

判定规则是纯函数，单测在 `scripts/endpoint-patrol.test.mjs`。
