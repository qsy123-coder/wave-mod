# 中国用户登录方案文档

## 1. 文档目标

本文档用于为「鸣潮角色 MOD 个人站」设计一套面向中国用户体验更好的登录方案，覆盖：

- 主流邮箱登录
- 微信登录
- QQ 登录
- 手机号登录

并结合当前项目技术栈进行落地建议：

- Next.js 16 App Router
- TypeScript
- Supabase Auth
- Supabase Database
- 中国用户为主的游戏内容站点

本文档只提供产品与技术方案，不直接修改现有登录代码。

---

## 2. 结论摘要

对于当前项目，最推荐的中国用户登录方案不是一次性把所有登录方式都接入，而是采用分阶段建设策略。

### 最佳体验优先级

1. 微信登录
2. 邮箱验证码登录
3. 手机号验证码登录
4. QQ 登录

### 最务实的上线顺序

#### 第一阶段
- 邮箱验证码登录
- 微信登录

#### 第二阶段
- 手机号验证码登录

#### 第三阶段
- QQ 登录

### 总体建议

短期优先做：

- 邮箱验证码登录
- 微信登录

中期再补：

- 手机号验证码登录

后期作为补充渠道：

- QQ 登录

原因是这套组合在中国用户体验、实现复杂度、上线速度和长期维护成本之间最平衡。

---

## 3. 当前项目现状

当前项目已经使用 Supabase Auth，现有登录方式为：

- 邮箱 OTP / Magic Link

现状特点：

1. 已具备基础认证能力。
2. 管理员登录目前依赖邮箱更稳定。
3. 普通中国用户对 magic link 的接受度通常弱于验证码登录。
4. 当前项目尚未接入微信、QQ、手机号登录。

因此后续的登录升级不建议推翻现有 Supabase Auth，而应尽量在现有身份体系上扩展。

---

## 4. 中国用户最优登录方案

## 4.1 邮箱登录

### 推荐形式

推荐采用：

- 邮箱验证码登录

不建议仅保留：

- 纯 Magic Link 登录

### 原因

中国用户对“输入邮箱后点击邮件链接登录”的理解成本较高，主要问题包括：

1. 需要跳转到邮箱 App 或网页邮箱。
2. QQ 邮箱、163 邮箱有时收信延迟或进入垃圾箱。
3. 手机端在浏览器和邮箱之间切换体验差。
4. 很多用户更习惯输入验证码，而不是点击链接。

### 建议体验

用户流程建议为：

1. 输入邮箱
2. 点击发送验证码
3. 收到 6 位验证码
4. 输入验证码完成登录

### 支持邮箱类型

建议明确在页面文案中提示支持：

- QQ 邮箱
- 163 邮箱
- 126 邮箱
- Outlook
- Gmail
- 企业邮箱

### 定位

邮箱登录适合作为：

- 管理员稳定登录方式
- 普通用户通用兜底登录方式
- 无需依赖国内社交平台审核的基础登录方式

### 结论

邮箱登录必须保留，但面向中国用户时应从 Magic Link 优先，调整为验证码优先。

---

## 4.2 微信登录

### 重要性

微信登录是中国用户体验最好的第三方登录方式之一，优先级最高。

### 优点

1. 用户熟悉度高。
2. 登录信任感强。
3. 移动端体验好。
4. 对内容站、工具站、社区站都有较高转化率。

### 适合本项目的方式

如果当前项目是标准 Web 站点，优先考虑：

- 网页微信登录
- PC 扫码登录为主

如果未来站点大量从微信内打开，再考虑：

- 公众号 OAuth 登录

### 适用场景

适合作为：

- 首页主推荐登录方式
- 普通用户首选快捷登录方式
- 面向移动端和国内用户的主社交登录入口

### 风险与注意点

1. 接入门槛高于邮箱。
2. 需要微信开放平台相关资质与配置。
3. 域名、备案、主体信息要更规范。
4. 回调地址和审核流程可能比邮箱复杂。

### 结论

微信登录应作为中国用户体验最佳方案中的第一优先级。

---

## 4.3 手机号登录

### 重要性

手机号验证码登录非常符合中国互联网用户习惯，用户理解成本极低。

### 优点

1. 登录门槛低。
2. 不依赖邮箱送达率。
3. 移动端体验非常自然。
4. 普通用户转化率通常较高。

### 缺点

1. 需要短信服务商。
2. 有真实短信成本。
3. 需要做频率限制和风控。
4. 有刷短信、恶意请求风险。

### 项目判断

对于当前项目，手机号登录非常值得做，但不建议压过微信和邮箱优先落地。原因是：

- 需要额外短信通道
- 有持续运营成本
- 风控复杂度高于邮箱

### 结论

手机号登录很适合中国用户，但建议放在邮箱 + 微信上线之后接入。

---

## 4.4 QQ 登录

### 价值

QQ 登录对二次元、游戏和年轻用户仍有一定价值。

你的项目是鸣潮 MOD 站，这类用户里 QQ 生态用户并不少，因此 QQ 登录不是无意义功能。

### 现实问题

1. 平台接入体验通常不如微信。
2. 长期维护价值通常低于微信。
3. 审核、回调、兼容性和文档体验可能更折腾。

### 适合作为

- 第四顺位补充登录方式
- 游戏用户、QQ 生态用户的补充入口

### 结论

QQ 登录可以做，但不建议抢在微信和手机号前面。

## 5. 推荐的总体产品方案

## 5.1 登录入口排序

登录页推荐按钮顺序：

1. 微信登录
2. 手机号验证码登录
3. 邮箱验证码登录
4. QQ 登录

如果你当前先做第一阶段，推荐先展示：

1. 微信登录
2. 邮箱验证码登录

手机号和 QQ 可先放“即将支持”或后续迭代。

---

## 5.2 管理员与普通用户分层建议

### 管理员

管理员建议长期保留：

- 邮箱验证码登录

原因：

1. 最稳定。
2. 不依赖第三方社交平台状态。
3. 更适合后台权限控制。
4. 更适合与 `ADMIN_EMAIL` 白名单策略结合。

### 普通用户

普通用户建议优先使用：

- 微信登录
- 邮箱验证码登录
- 后续手机号验证码登录

---

## 5.3 登录页文案建议

建议不要写技术性术语，而要用更符合中国用户的表达：

- 微信快捷登录
- 手机号验证码登录
- 邮箱验证码登录
- QQ 登录

管理员区域可增加说明：

- 管理员建议使用邮箱登录，稳定性更高

## 6. 推荐技术路线

## 6.1 总原则

推荐继续以 Supabase Auth 作为统一身份中心，不建议当前阶段重做整套用户体系。

### 原因

1. 当前项目已经在用 Supabase Auth。
2. 收藏、评论、点赞、评分等用户行为未来都依赖稳定用户 ID。
3. 保持 Supabase Auth 作为统一身份层，能降低重构成本。
4. 后续无论接邮箱、微信、手机号还是 QQ，都应尽量收敛到同一套站内用户身份。

---

## 6.2 推荐路线

### 路线 A：继续以 Supabase Auth 为主

适合当前项目。

承载：

- 邮箱验证码登录
- 手机号验证码登录
- 标准 OAuth 登录
- 第三方登录后的统一会话管理

### 优点

1. 用户体系统一。
2. Session 统一。
3. 收藏、评论、RLS、后台权限逻辑不需要推翻。
4. 开发成本最低。

### 缺点

1. 中国平台 OAuth 的直接支持可能有限。
2. 微信、QQ 可能需要桥接层。
3. 短信服务常常需要国内服务商配合。

### 结论

当前阶段推荐继续让 Supabase Auth 作为最终身份中心。

---

## 6.3 不建议当前就走的路线

### 路线 B：完全自建中国本地认证中心

例如：

- 微信 / QQ / 手机号先在自定义服务里做认证
- 再自行维护用户、会话、绑定关系
- 最后再与 Supabase 数据层拼接

### 不建议原因

1. 实现复杂度高。
2. 账号绑定与合并逻辑更复杂。
3. 与现有 Supabase Auth 体系冲突更大。
4. 对当前项目阶段而言投入过大。

---

## 7. 账号体系建议

无论接多少登录方式，最终都应该合并到同一个站内账号。

### 目标能力

后续建议支持：

1. 同一用户多登录方式绑定。
2. 微信 + 邮箱 + 手机号绑定到同一账号。
3. 首次登录自动创建 profile。
4. 后台管理员继续走邮箱白名单逻辑。
5. 登录方式可扩展，但用户 ID 唯一。

### 为什么重要

否则会出现问题：

- 用户用微信登录有一个账号
- 用邮箱登录又生成一个账号
- 收藏、评论、点赞数据分散

这会严重影响后续社区体验。

---

## 8. 风控建议

## 8.1 邮箱验证码风控

建议至少具备：

1. 单邮箱发送频率限制
2. 单 IP 发送频率限制
3. 验证码有效期
4. 多次输错锁定
5. 中文错误提示

## 8.2 手机号验证码风控

建议至少具备：

1. 单手机号发送频率限制
2. 单 IP 限流
3. 图形验证码或行为验证码
4. 冷却时间
5. 黑名单能力

## 8.3 第三方登录风控

1. 严格校验 state
2. 限制回调域名
3. 服务端校验 provider 返回身份
4. 绑定时要求用户确认

## 9. 推荐实施阶段

## 阶段 A：邮箱中国化升级（已完成第一步页面体验改造）

### 目标

把当前邮箱 Magic Link / OTP 体验升级为更适合中国用户的邮箱验证码登录体验。

### 包含内容

1. 登录页改成邮箱验证码优先。
2. 全部文案中文化。
3. 明确支持 QQ/163/126/Outlook/Gmail。
4. 增加验证码发送状态、倒计时和错误提示。
5. 管理员登录流程继续优先邮箱。

### 当前完成情况

- 阶段 16 已完成第一步页面体验改造：登录页改为“邮箱验证码登录”表达，支持 QQ 邮箱、163、126、Outlook、Gmail、企业邮箱提示。
- 已增加发送成功说明、60 秒重新发送倒计时、收不到邮件提示和管理员邮箱登录说明。
- 当前仍复用 Supabase `signInWithOtp()` 与既有回调链路，未修改 Provider 配置或邮件服务商配置。
- 后续如需要真正的站内 6 位验证码输入框，应继续评估 Supabase 邮件模板、OTP 验证模式和邮件送达服务商配置。

### 预期收益

- 低成本提升登录可用性
- 不依赖微信/QQ 审核即可先上线

---

## 阶段 B：微信登录接入（已完成最小入口与配置边界）

### 目标

接入中国用户主社交登录方式。

### 包含内容

1. 增加微信登录按钮。
2. 完成微信网页登录流程。
3. 登录后自动创建或绑定站内用户。
4. 与现有 Supabase Auth 会话打通。

### 当前完成情况

- 阶段 17 已完成最小微信登录入口与配置边界。
- 已确认 Supabase Auth 当前官方外部 Provider 列表不包含微信，无法直接通过 `provider: "wechat"` 原生接入。
- 登录页在普通用户模式展示“微信快捷登录”按钮；管理员模式继续仅推荐邮箱登录。
- 新增 `WECHAT_AUTH_BRIDGE_URL` 作为后续自定义微信认证桥接地址；未配置时返回登录页并展示“微信登录尚未配置”的明确提示。
- 本阶段没有申请或配置真实微信开放平台 AppID / AppSecret / 回调域名，没有伪造可用微信登录。

### 后续真实接入清单

1. 申请微信开放平台网站应用。
2. 准备备案域名和回调域名。
3. 实现微信 OAuth 桥接服务：跳转微信授权、校验 state、换取 openid/unionid、映射站内用户。
4. 设计桥接服务与 Supabase Auth 的会话打通方式。
5. 阶段 20 账号绑定时统一处理微信、邮箱、手机号、QQ 的账号合并。

### 预期收益

- 提升普通用户登录转化
- 降低内容互动门槛

---

## 阶段 C：手机号验证码登录（已完成最小入口与配置边界）

### 目标

补齐中国用户最常见的登录方式。

### 包含内容

1. 接入短信服务商。
2. 登录页增加手机号验证码入口。
3. 完成频率限制和风控。
4. 与现有账号绑定体系打通。

### 当前完成情况

- 阶段 18 已完成手机号验证码登录最小入口与配置边界。
- 已验证阿里云 `Dypnsapi SendSmsVerifyCode` 接口可正常发送验证码，并新增服务端封装 `src/lib/sms/aliyun-dypns.ts`。
- 已按正式登录路线新增 Supabase Send SMS Hook + 阿里云普通短信 `Dysmsapi SendSms` 封装：`src/lib/sms/aliyun-dysms.ts`、`src/app/api/auth/sms/send/route.ts`。
- 已确认 Supabase Auth 支持 `signInWithOtp({ phone })` 发送短信验证码，并通过 `verifyOtp({ phone, token, type: "sms" })` 验证登录。
- 登录页普通用户模式新增手机号验证码区域：发送短信验证码、输入 6 位验证码、验证并登录。
- 新增 `ENABLE_SUPABASE_PHONE_OTP` 开关，默认关闭；未启用时会显示配置缺失提示，不会伪造可用短信登录。
- 当前只支持中国大陆 11 位手机号或 `+86` 格式归一化。

### 后续真实接入清单

1. 在 Supabase Auth 中启用 Phone Provider。
2. 在 Supabase Auth Hooks 中配置 Send SMS Hook，地址为生产域名下的 `/api/auth/sms/send`。
3. 将 Supabase 生成的 `SUPABASE_SEND_SMS_HOOK_SECRET` 写入服务端环境变量。
4. 配置阿里云普通短信 `ALIYUN_DYSMS_SIGN_NAME`、`ALIYUN_DYSMS_TEMPLATE_CODE`，模板变量需要包含 `${code}`。
5. 针对中国大陆用户评估实际送达率和费用。
6. 增加服务端和边缘层风控：手机号限流、IP 限流、验证码输错限制、冷却时间和黑名单能力。
7. 阶段 20 账号绑定时统一处理手机号与邮箱、微信、QQ 的账号合并。

### 预期收益

- 移动端转化提升
- 用户登录阻力继续下降

## 10. 最终推荐决策

对于当前项目，推荐明确采用以下方案：

### 最推荐的产品方案

- 主登录方式：微信登录
- 稳定兜底方式：邮箱验证码登录
- 第二批增强：手机号验证码登录
- 后续补充：QQ 登录

### 最推荐的技术方案

- 保持 Supabase Auth 作为统一身份中心
- 不推翻现有登录体系
- 通过分阶段方式接入中国用户偏好的登录入口
- 所有登录方式最终合并到同一个站内账号

### 最推荐的上线顺序

1. 邮箱验证码登录
2. 微信登录
3. 手机号验证码登录
4. QQ 登录

如果考虑“最快上线 + 中国用户体验”，当前最优组合是：

- 第一版上线：邮箱验证码登录 + 微信登录

## 12. 一句话结论

对于中国用户体验最好的方案，不是“把所有登录方式一次做完”，而是：

- 先用邮箱验证码保证稳定可用
- 用微信提升中国用户主体验
- 再用手机号提升转化
- 最后补 QQ

并始终保持 Supabase Auth 作为统一账号中心。
